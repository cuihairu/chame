# 1. 项目定位与设计目标\
\
## 1.1 产品定位\
\
Chame 是使用 Go 构建游戏后端服务的通用框架。它为游戏服务提供可组合的运行时、模块生命周期管理、依赖装配、基础设施抽象，以及可选的区块链集成能力。\
\
Chame 不等于区块链 SDK，也不是一套固定游戏玩法的完整服务端产品。\
\
它需要同时解决三个层面的问题：\
\
1. **游戏后端运行基础设施**：应用启动、配置、生命周期、依赖注入、模块管理、日志、健康检查等。\
2. **可选的区块链能力**：账户、网络、资产查询、交易提交、链上事件、最终性和签名能力。\
3. **开发者自己的游戏业务**：玩家、角色、道具、战斗、房间、匹配、排行榜、游戏经济、充值、提取等业务由项目自行决定。\
\
第三层不应被框架的默认业务模型限制。\
\
## 1.2 核心目标\
\
- 允许开发者创建自己的游戏后端项目。\
- 允许游戏业务模块在不依赖具体链 SDK 的情况下调用链能力。\
- 同一 EVM 适配器可以接入多个 EVM 网络实例。\
- Solana 通过独立适配器实现，不伪装成 EVM。\
- 支持自定义链适配器、游戏模块和基础设施实现。\
- 具备明确的异步交易状态、幂等语义和故障恢复机制。\
- 支持从最小应用逐步扩展，不要求开发者一次启用所有模块。\
- 提供可选脚手架，但不将生成器作为运行时依赖。\
- 允许开发者替换数据库、消息组件、签名服务和 RPC 提供方。\
\
## 1.3 非目标\
\
首期不要求实现：\
\
- 固定的 MMO、房间制、棋牌、塔防或其他游戏业务模型。\
- 统一规定所有游戏资产的结构。\
- 强制所有游戏使用同一种数据库。\
- 自研区块链节点或共识算法。\
- 将 EVM 和 Solana 的交易、账户、公钥、最终性语义强行统一成完全相同的模型。\
- 内置托管用户私钥的中心化钱包产品。\
- 默认内置代币经济、市场、NFT 商城、充值提现业务。\
- 强制引入微服务、Kubernetes、消息队列或特定云平台。\
- 依赖代码生成器才能编译或运行。\
- 由框架自动生成游戏业务规则。\
\
这些能力未来可以由独立模块或外部产品提供，但不属于首期核心要求。\
\
## 1.4 基本设计原则\
\
### 原则 A：核心层不依赖具体链\
\
Core 不导入 EVM 或 Solana SDK。具体链 SDK 只能存在于对应适配器的实现层。\
\
### 原则 B：公共抽象不抹平关键差异\
\
可以统一调用方式，但必须保留链特有的数据、错误、确认状态和交易语义。\
\
例如，EVM 的区块高度、区块哈希、交易回执与 Solana 的 slot、签名、confirmation status 应保留各自的语义。\
\
### 原则 C：模块可选，而非强制完整套装\
\
一个只需要 HTTP API 的游戏服务，不应因为采用 Chame 而必须启动区块链监听器、数据库和后台任务。\
\
### 原则 D：业务归业务，框架归框架\
\
框架可以提供交易编排、幂等工具和事件交付基础设施，但不能规定“道具就是 NFT”“玩家资产必须上链”等业务结论。\
\
### 原则 E：可靠性优先于表面上的统一\
\
网络请求超时不代表链上交易失败；交易已提交不代表交易已确认；交易已确认也不一定等于业务所需的最终性。\
\
这些状态必须明确区分。\

# 2. 总体架构\
\

## 2.2 模块依赖规则\
\
允许：\
\
- Game Application → Chame 公共 API。\
- Game Module → Core 和其声明的能力接口。\
- Adapter → Core 接口和自身所需的链 SDK。\
- Infrastructure Adapter → 对应的基础设施接口。\
- Composition Root → 具体实现，用于装配依赖。\
\
禁止：\
\
- Core → EVM SDK。\
- Core → Solana SDK。\
- 游戏业务包 → 具体链 SDK，除非开发者明确选择绕过公共抽象。\
- EVM Adapter → Solana Adapter。\
- Solana Adapter → EVM Adapter。\
- 模块之间通过隐式全局变量访问内部状态。\
- 通过包级全局单例实现不可替换的数据库、RPC 客户端或签名器。\
\
## 2.3 两类不同的扩展点\
\
Chame 必须区分以下概念。\
\
**Module：业务或应用能力模块**\
\
负责注册业务服务、API、事件处理器、后台任务和运行时资源。例如自定义的排行榜模块、玩家模块或链上资产业务模块。\
\
**Adapter：基础设施或协议适配器**\
\
负责实现既定接口。例如 EVM Adapter、Solana Adapter、PostgreSQL Adapter、自定义 RPC Adapter。\
\
两者不能混为一谈。一个模块可以依赖某个抽象接口，但不应自行复制另一套基础设施适配器。\

## 3.1 目录规则\
\
- `core/` 只包含框架运行基础设施，不放具体游戏业务。\
- `capability/` 定义可替换的公共能力契约。\
- `adapters/` 实现具体链协议适配。\
- `infrastructure/` 放数据库、签名器和可观测性等基础设施实现。\
- `application/` 放可复用的应用编排能力，例如交易状态协调和事件交付。\
- `examples/` 是可运行示例，不应被运行时依赖。\
- `templates/` 只提供可选项目骨架。\
- `tools/` 放可选开发工具；主框架不得在运行时调用它们。\
- `tests/conformance/` 用于验证所有适配器遵守相同的公共契约。\
- 如果仓库规模较小，可以暂时不建立所有空目录，避免为目录而目录。\
\
## 3.2 Go Module 规则\
\
模块路径以仓库的实际 `go.mod` 为准。不要擅自假设最终 GitHub URL。\
\
所有公开包应遵循：\
\
- 小而明确的接口。\
- 接口以使用方需要的行为为依据。\
- 避免一个包含几十个方法的超级接口。\
- 避免无意义的 `BaseXxx`、`Manager`、`Factory` 层层包装。\
- 不为未来可能出现的功能提前建立大量空抽象。\
- 公开 API 在稳定前通过测试和文档确认。\

# 4. Runtime 设计\
\
## 4.1 Runtime 的职责\
\
Runtime 是 Chame 应用的生命周期容器，负责：\
\
- 接受模块注册。\
- 校验模块依赖。\
- 确定模块初始化和关闭顺序。\
- 创建应用级上下文。\
- 启动模块。\
- 协调健康状态。\
- 接收停止信号并优雅关闭。\
- 防止同一 Runtime 重复启动。\
- 在启动失败时清理已成功启动的模块。\
\
Runtime 不负责：\
\
- 直接执行业务逻辑。\
- 自动创建所有基础设施。\
- 隐式发现任意目录下的模块。\
- 替开发者选择链、数据库或签名策略。\
- 把所有后台任务放在一个不可控的 goroutine 中。\
\
## 4.2 生命周期状态\
\
```text\
New\
 │\
 ▼\
Configuring\
 │\
 ▼\
Initializing\
 │\
 ▼\
Starting\
 │\
 ▼\
Running\
 │\
 ▼\
Stopping\
 │\
 ▼\
Stopped\
```\
\
任何初始化或启动阶段失败，都必须返回带有模块名称和失败阶段的错误。\
\
状态规则：\
\
- `New`：允许注册模块。\
- `Configuring`：完成配置合并和校验。\
- `Initializing`：创建模块资源，不应启动不可控的长期任务。\
- `Starting`：按依赖顺序启动模块。\
- `Running`：正常提供服务。\
- `Stopping`：拒绝新任务，停止接收新请求，完成可完成的工作。\
- `Stopped`：资源已关闭，不允许重复启动同一实例。\
\
首期不支持在运行中的 Runtime 上任意热插拔模块。模块增删需要重建 Runtime，避免复杂的依赖变更和资源竞争。\
\
## 4.3 Module 接口\
\
建议从最小接口开始：\
\
```go\
package module\
\
import \

=====

\
)\
\
type NetworkID struct {\
    Family  ChainFamily\
    Name    string\
    ChainID string\
}\
```\
\
说明：\
\
- `Family` 标明链族。\
- `Name` 是应用配置中的稳定逻辑名称。\
- `ChainID` 是链族内的协议标识，使用字符串避免公共层受限于某种整数宽度。\
- 生产环境应额外验证 RPC 返回的链标识与配置一致。\
- `Name` 不是链的密码学身份，不应单独用于验证资产或签名目标。\
\
EVM 的 Chain ID 是协议身份的一部分。Solana 的集群配置需要通过可信的 Genesis Hash 等信息进行识别和校验；`mainnet-beta` 只是配置标签。\
\
## 6.3 地址模型\
\
不同链地址不可混用。\
\
建议使用带链族语义的类型：\
\
```go\
type Address struct {\
    Family ChainFamily\
    Value  string\
}\
```\
\
公共层不得对所有地址统一调用同一种大小写转换。\
\
- EVM 地址需要校验长度和十六进制格式，并在适用时校验 EIP-55 格式。\
- Solana 地址需要按其编码规则校验公钥表示。\
- 地址比较必须由链族感知的实现负责。\
- 地址存储应保留可验证的规范表示。\
- 用户输入地址不能仅通过去掉空格或统一大小写就认为有效。\
\
## 6.4 数值与精度\
\
禁止使用 `float32` 或 `float64` 表示链上资产金额。\
\
EVM Token 通常以整数最小单位表达数量，Solana Token 也应使用原始整数数量及对应精度。\
\
建议定义：\
\
```go\
type Amount struct {\
    Raw       string\
    Decimals  uint8\
    AssetID   string\
}\
```\
\
这里的 `Raw` 是十进制整数的字符串表示，避免公共模型依赖任意精度整数在 JSON 中的编码方式。\
\
要求：\
\
- `Raw` 必须符合无符号整数或业务明确支持的有符号整数规则。\
- 资产精度来自可信的资产元数据，不可默认所有资产均为 18 位。\
- 金额运算必须采用精确整数或任意精度运算。\
- 格式化为人类可读金额时，不能把展示值反向作为链上提交金额。\
- 不同资产的金额不可直接相加。\
- 资产标识必须包含链和资产定位信息。\
\
## 6.5 资产标识\
\
建议：\
\
```go\
type AssetID struct {\
    Network NetworkID\
    Kind    string\
    Address string\
}\
```\
\
`Kind` 可表示原生资产、EVM Token、Solana SPL Token 等类型。\
\
对原生资产，可以使用明确且经过校验的约定值；不得把空地址在所有链上都视为原生资产。\
\
游戏中的资产实体与链上资产必须分离：\
\
```text\
Game Asset ID\
      │\
      ▼\
Game Asset Model\
      │\
      ├── Optional mapping ──> EVM Token\
      │\
      └── Optional mapping ──> Solana Token / Program Account\
```\
\
Chame 不应默认一个游戏道具对应一个 NFT，也不应强制要求所有游戏资产都上链。\

# 5. 配置系统\
\
## 5.1 设计要求\
\
配置应支持：\
\
- 显式配置结构体。\
- 默认值。\
- 环境变量覆盖。\
- 文件配置。\
- 启动前校验。\
- 敏感字段保护。\
- 配置来源追踪。\
- 测试时直接构造配置对象。\
\
建议优先使用 Go 原生结构体与显式校验，不要为了配置系统引入过度复杂的表达式语言。\
\
## 5.2 配置优先级\
\
默认优先级从低到高：\
\
1. 代码中的默认值。\
2. 配置文件。\
3. 环境变量。\
4. 启动参数中的显式覆盖值。\
\
如引入远程配置服务，必须作为独立可选模块，不纳入首期强制依赖。\
\
## 5.3 示例配置\
\
```yaml\
app:\
  name: example-game\
  environment: development\
  shutdown_timeout: 20s\
\
logging:\
  level: info\
  format: json\
\
chains:\
  evm:\
    - name: ethereum-mainnet\
      chain_id: 1\
      rpc_urls:\
        - ${EVM_RPC_URL}\
      timeout: 10s\
      read_only: true\
\
    - name: base-mainnet\
      chain_id: 8453\
      rpc_urls:\
        - ${BASE_RPC_URL}\
      timeout: 10s\
      read_only: true\
\
  solana:\
    - name: solana-mainnet\
      cluster: mainnet-beta\
      rpc_urls:\
        - ${SOLANA_RPC_URL}\
      commitment: confirmed\
      read_only: true\
\
transactions:\
  enabled: false\
\
events:\
  enabled: false\
```\
\
该配置只是结构示例，不意味着所有字段名称已永久冻结。\
\
## 5.4 配置校验\
\
必须拒绝：\
\
- 缺失必需的网络标识。\
- 重复的逻辑网络名称。\
- 不合法的 URL。\
- 无效的超时时间。\
- 交易功能启用但未配置所需签名能力。\
- 不安全的生产环境默认配置。\

## 6.1 设计目标\

# 7. EVM Adapter\
\
## 7.1 定位\
\
EVM Adapter 是一个适配器实现，可以配置多个 EVM 网络实例。\
\
例如：\
\
- Ethereum Mainnet\
- Base\
- Arbitrum\
- Optimism\
- Polygon\
- 其他兼容 EVM 的网络\
\
是否支持某个网络，取决于 RPC 兼容性、所需协议能力和适配器测试结果，而不是仅凭它宣称兼容 EVM。\
\
## 7.2 主要职责\
\
- 连接 EVM JSON-RPC。\
- 校验 Chain ID。\
- 查询区块与网络信息。\
- 查询原生资产余额。\
- 查询 Token 余额及元数据。\
- 构建、签名和提交交易。\
- 查询交易回执。\
- 读取事件日志。\
- 处理区块重组。\
- 处理 Nonce 协调。\
- 实现可配置的确认与最终性策略。\
- 提供合约调用的基础能力。\
\
## 7.3 多网络模型\
\
同一个 EVM Adapter 应支持多个独立的 Network Instance。\
\
每个实例拥有：\
\
- 逻辑网络名称。\
- Chain ID。\
- RPC Endpoint 池。\
- 超时和重试策略。\
- 限流配置。\
- 读写权限。\
- 最终性策略。\
- 健康状态。\
- 可选的签名器绑定。\
\
不能把一个 EVM Adapter 的全局 Chain ID 固定为单值。\
\
## 7.4 RPC Endpoint 管理\
\
建议抽象 Endpoint Pool，具备：\
\
- 多 Endpoint 配置。\
- 健康检查。\
- 请求超时。\
- 按请求类型进行限流。\
- 可选的故障切换。\
- 错误分类。\
- 连接复用。\
- 指标记录。\
\
注意事项：\
\
- 切换 Endpoint 不代表原交易没有提交。\
- 读取操作可在安全条件下重试。\
- 发送交易前后必须识别可能的提交不确定性。\
- Endpoint 故障不能直接推断链发生故障。\
- 如果不同 Endpoint 返回互相矛盾的链数据，应记录异常并避免静默选择错误结果。\
\
## 7.5 Nonce 管理\
\
EVM 交易发送必须正确处理账户 Nonce。\
\
首期应明确区分：\
\
- 从链上查询到的账户 Nonce。\
- 本地已分配但尚未提交的 Nonce。\
- 已提交但结果未知的交易。\
- 已确认的交易。\
- 需要重新提交或人工处理的交易。\
\
如果支持同一账户的并发交易，不能让多个 goroutine 各自读取链上 Nonce 后独立发送。\
\
建议实现可替换的 Nonce Coordinator：\
\
- 按 Network ID + Sender Address 进行隔离。\
- 提供账户级并发控制。\
- 为每次本地分配保留可恢复记录。\
- 区分“交易构建失败”和“交易可能已经广播”。\
- 不得在超时后盲目递增或重置 Nonce。\
- 对替换交易、加价重发和取消交易提供明确状态。\
- 多实例部署时，必须使用共享协调机制或明确限定单实例写入；单机内存锁不能解决跨进程竞争。\
\
首期如果不实现多实例协调，应在文档中明确限制，不得宣称天然支持分布式并发写入。\
\
## 7.6 EVM 交易参数\
\
至少需要考虑：\
\
- Chain ID。\
- Sender。\
- Recipient 或合约地址。\
- Value。\
- Calldata。\
- Gas Limit。\
- Gas Price 或 EIP-1559 费用字段。\
- Nonce。\
- Access List（可选）。\
- 签名器。\
- 交易提交期限。\
- 应用幂等键。\
\
不能把 EIP-1559 费用字段强加给不支持该机制的网络。\
\
## 7.7 合约调用\
\
合约交互分为：\
\
1. 只读调用。\
2. 状态变更交易。\
3. 事件读取。\
4. ABI 编码与解码。\
5. 可选的特定合约业务封装。\
\
基础适配器提供通用 EVM 能力，但不要把游戏资产、市场、NFT、充值等业务固化在 EVM Adapter 内。\
\
特定合约可由独立的 ContractAdapter 封装。\
\
## 7.8 EVM 最终性\
\
不要把交易被打包直接等同于最终成功。\
\
至少区分：\
\
- Pending：尚未确认结果。\
- Included：已包含在区块中。\
- Confirmed：达到应用配置的确认要求。\
- Finalized：达到网络支持的最终性要求。\
- Reverted：执行失败。\
- Reorged：原先观察到的区块被重组移除。\
- Unknown：无法可靠判断当前状态。\
\
`Finalized` 的具体语义必须由适配器与网络能力共同定义。\
\
对于无法提供明确 finalized 标签的网络，可以采用可配置的确认深度策略，但必须说明这只是应用层策略，不能保证所有共识条件下绝对不可逆。\

# 8. Solana Adapter\
\
## 8.1 定位\
\
Solana 是独立适配器，不应被包装成 EVM Adapter 的一个特殊网络。\
\
它具有自己的：\
\
- 公钥与地址体系。\
- 账户模型。\
- Program 调用模型。\
- 交易消息与签名格式。\
- Recent Blockhash 与有效期限。\
- Slot 与区块概念。\
- Commitment 与确认状态。\
- Token Program 及其账户模型。\
\
公共层只统一业务需要的能力，不统一这些协议内部细节。\
\
## 8.2 主要职责\
\
- 连接 Solana RPC。\
- 校验集群身份。\
- 查询账户与余额。\
- 查询 SPL Token 账户。\
- 构建交易消息。\
- 请求签名。\
- 提交序列化交易。\
- 查询签名状态。\
- 读取交易与日志。\
- 处理 Blockhash 过期。\
- 处理交易提交结果未知。\
- 提供可配置的确认策略。\
\
## 8.3 Solana 交易流程\
\
```text\
构建交易指令\
    │\
    ▼\
构建 Message\
    │\
    ▼\
获取 Recent Blockhash\
    │\
    ▼\
确定所需签名者\
    │\
    ▼\
签名并序列化\
    │\
    ▼\
提交 RPC\
    │\
    ▼\
记录 Signature\
    │\
    ▼\
轮询或订阅确认状态\
    │\
    ├── 成功并达到要求 → 完成\
    ├── 程序执行失败     → 失败\
    ├── Blockhash 过期   → 按策略恢复\
    └── 结果未知         → 查询与对账\
```\
\
## 8.4 Blockhash 过期\
\
Blockhash 过期不等于交易已执行，也不等于一定没有执行。\
\
恢复逻辑应：\
\
1. 保留原交易签名和最近一次有效期限信息。\
2. 查询原签名是否已被链接受。\
3. 根据适配器支持的 RPC 能力判断状态。\
4. 仅在确认旧交易不可能再生效或已可靠判定未执行时，才允许重新构建新交易。\
5. 如果状态仍不确定，保留 `Unknown` 并继续对账，不能自动重复执行可能产生业务副作用的交易。\
\
## 8.5 Commitment\
\
Solana 的 `processed`、`confirmed`、`finalized` 不能与 EVM 的确认深度直接等价。\
\
应用应明确选择业务需要的确认等级，并将实际观察到的状态和最终采用的业务状态分别记录。\

# 10. 幂等、持久化与恢复\
\
## 10.1 幂等键\
\
每个需要可靠执行的链上操作都应支持应用级幂等键。\
\
建议幂等作用域：\
\
```text\
Application / Tenant\
    + Operation Type\
    + Idempotency Key\
```\
\
数据库应对该作用域建立唯一约束。\
\
规则：\
\
- 相同幂等键、相同业务请求：返回已有操作结果或当前状态。\
- 相同幂等键、不同业务请求：返回明确冲突错误。\
- 操作进入不确定状态时：不得因为 HTTP 超时就创建第二笔独立操作。\
- 幂等记录应保留足够长的时间，不能随意短期过期导致重复执行。\
\
## 10.2 持久化接口\
\
建议抽象：\
\
```go\
type TransactionRepository interface {\
    Create(ctx context.Context, tx TransactionRecord) error\
    Get(ctx context.Context, id TransactionID) (TransactionRecord, error)\
    FindByIdempotencyKey(\
        ctx context.Context,\
        scope IdempotencyScope,\
        key string,\
    ) (TransactionRecord, error)\
    UpdateStatus(\
        ctx context.Context,\
        id TransactionID,\
        expected TransactionStatus,\
        next TransactionStatus,\
    ) error\
}\
```\
\
实际实现必须支持并发条件更新，避免多个 Worker 同时把同一操作推进到互相矛盾的状态。\
\
## 10.3 持久化原则\
\
- 首期可提供 Memory Repository 方便测试和最小示例。\
- Memory Repository 不具备进程重启后的恢复能力。\
- 生产交易工作流必须使用持久化实现。\
- 关系数据库可作为首个官方生产级持久化实现，但不意味着框架只能支持关系数据库。\
- 业务数据库与框架内部操作存储可以共用同一数据库，也可以分离。\
- 数据库事务不能与区块链交易形成一个原子分布式事务。\
- 需要通过持久化状态、幂等键、Outbox（如有事件投递需求）和对账实现最终一致性。\
\
## 10.4 恢复 Worker\
\
恢复任务应扫描：\
\
- 长时间停留在 `Prepared` 的操作。\
- 已签名但尚未确认提交的操作。\
- 提交结果未知的操作。\
- 已提交但长时间没有新观察结果的操作。\
- 已包含但未达到最终性要求的操作。\
- 可能受到链重组影响的事件。\
- 需要重新投递的业务事件。\
\
恢复任务必须具备：\
\
- 可配置扫描间隔。\
- 分页和批处理。\
- 任务领取或租约机制。\
- 最大并发限制。\
- 退避策略。\
- 任务超时。\
- 指标与日志。\
- 可人工触发的对账入口。\
\
多实例部署时必须防止多个 Worker 无约束地重复处理同一任务。\

## 11.1 事件来源\

- Solana 交易日志及适配器能够可靠提供的相关事件来源。\

\
## 11.2 事件记录\
\
建议记录：\
\
- Network ID。\
- 事件来源类型。\
- 交易 ID 或签名。\
- 区块哈希或 slot 等链特定位置。\
- 区块高度或 slot。\
- 交易内事件索引（如可获得）。\
- 规范化事件类型。\
- 原始事件数据。\
- 解码版本。\
- 观察时间。\
- 当前链上观察状态。\
- 最终性状态。\
- 处理状态。\
- 处理尝试次数。\
\
## 11.3 事件唯一标识\
\
不能只用交易哈希作为唯一事件标识，因为一笔交易可能产生多个事件。\
\
建议由适配器生成链族感知的事件定位键，例如：\
\
- EVM：Network + Block Hash + Transaction Hash + Log Index。\
- Solana：Network + Signature + 交易内可确定的事件位置；如果来源无法稳定提供唯一索引，应采用明确记录来源和解码位置的策略。\
\
对于可能被重组的事件，还必须保存足够的信息来撤销或重算相关业务投影。\
\
## 11.4 事件处理语义\
\
首期以 **至少一次交付 + 幂等消费** 为可靠性基线。\
\
不要声称普通数据库与区块链之间存在天然的 exactly-once 原子交付。\
\
处理流程：\
\
```text\
读取链上数据\
    │\
    ▼\
写入持久化事件记录\
    │\
    ▼\
识别重复事件\
    │\
    ▼\
按配置等待确认 / 最终性\
    │\
    ▼\
交付给业务 Handler\
    │\
    ├── 成功 → 标记完成\
    └── 失败 → 重试 / 进入待处理队列\
```\
\
事件 Handler 必须可以重复执行。业务模块应利用事件 ID、业务唯一键或事务约束实现幂等。\
\
## 11.5 游标和断点续传\
\
每个网络、每个事件来源应独立维护消费游标。\
\
EVM 可以使用区块高度和区块哈希追踪进度；Solana 应采用适配器能够可靠恢复的签名、slot 或 RPC 游标策略。\
\
游标不能只记录一个整数，而忽略重组和来源语义。\
\
断点续传要求：\
\
- 在事件持久化后再推进可恢复的处理进度。\
- 崩溃后能够重新读取最近一段数据。\
- 重复读取不产生重复业务效果。\
- 对游标回退或区块哈希不一致有检测机制。\
\
## 11.6 链重组\
\
EVM 事件处理需要考虑区块重组。\
\
当已观察到的区块不再属于当前链时：\
\
1. 识别受影响的事件。\
2. 将相关观察标记为失效或重组。\
3. 阻止尚未完成的业务处理继续推进为最终状态。\
4. 根据业务处理策略撤销、补偿或重算派生数据。\
5. 回退安全游标并重新扫描。\
6. 保存审计记录。\
\
不能假定所有游戏业务都可以自动回滚。对于已经发放奖励、发送外部消息或执行其他不可逆操作的业务，应由应用层定义补偿策略。\
\

# 12. Signer 与密钥安全\
\
## 12.1 核心要求\
\
签名能力必须独立于链 RPC 与业务模块。\
\
建议定义 `Signer` 能力接口，并由适配器明确它支持的签名类型、地址来源和交易格式。\
\
## 12.2 可插拔签名实现\
\
首期可以支持：\
\
- 测试专用签名器。\
- 本地开发签名器。\
- 外部签名服务接口。\
\
后续可以增加：\
\
- KMS。\
- HSM。\
- 托管钱包或 MPC 服务适配器。\
- 其他外部密钥管理服务。\
\
不要在核心框架中直接实现一套未经充分审查的复杂密钥托管系统。\
\
## 12.3 权限与签名边界\
\
- 游戏业务模块不应自动获得所有签名权限。\
- 读 RPC 与写 RPC 应允许分离。\
- 签名器应能限制可用网络和账户。\
- 交易发起应明确目标网络和目标账户。\
- 签名器不得仅凭调用方提供的任意数据就被认为授权成功。\
- 签名请求应可审计。\
- 生产日志不得记录私钥、助记词或完整秘密材料。\
- 配置系统不应把密钥秘密作为普通字符串到处复制。\
\
## 12.4 本地开发密钥\
\
本地签名器只用于开发、测试或明确允许的环境。\
\
生产环境应默认禁止从示例配置直接启用明文私钥签名。\
\
如果提供本地开发签名器，必须明确其风险、使用限制及安全配置。\
\

# 13. AccountProvider 与 AssetProvider\
\
## 13.1 AccountProvider\
\
账户能力至少应区分：\
\
- 链上地址。\
- 账户查询。\
- 账户余额。\
- 账户是否由某个 Signer 管理。\
- 链特有的账户信息。\
\
不要把“地址”与“私钥账户”视为同一个概念。\
\
某些链上账户可以是外部拥有账户、程序控制账户或合约账户；框架应保留这些差异。\
\
## 13.2 AssetProvider\
\
首期可提供只读能力：\
\
- 原生资产余额。\
- EVM Token 余额。\
- Solana SPL Token 余额。\
- 资产精度和元数据查询。\
- 资产标识与网络标识关联。\
\
写操作和资产转移应通过交易能力完成，不应让 `AssetProvider` 隐式产生链上副作用。\
\
## 13.3 资产业务边界\
\
框架不决定：\
\
- 道具是否可以交易。\
- 游戏币是否上链。\
- NFT 是否代表游戏物品。\
- 资产是否可提现。\
- 充值是否发放游戏币。\
- 链上余额如何映射到游戏余额。\
\
这些都是应用业务规则。Chame 只提供可靠的链交互能力和必要的编排基础设施。\
\

# 14. 错误体系\
\
## 14.1 错误分类\
\
建议建立稳定的错误类别：\
\
- `InvalidArgument`\
- `InvalidConfiguration`\
- `UnsupportedCapability`\
- `NetworkUnavailable`\
- `RequestTimeout`\
- `RateLimited`\
- `AuthenticationFailed`\
- `PermissionDenied`\
- `TransactionRejected`\
- `TransactionExecutionFailed`\
- `TransactionExpired`\
- `TransactionStatusUnknown`\
- `IdempotencyConflict`\
- `PersistenceFailure`\
- `EventDecodeFailure`\
- `EventProcessingFailure`\
- `FinalityNotReached`\
- `ReorgDetected`\
- `InternalError`\
\
这是一组公共分类，不要求所有底层错误都直接映射成同一个 Go error 字符串。\
\
## 14.2 错误要求\
\
- 使用可检查的错误类型或稳定错误代码。\
- 保留底层错误作为 cause。\
- 允许通过 `errors.Is` / `errors.As` 识别错误。\
- 错误信息应包含操作阶段。\
- 错误中不得泄露秘密材料。\
- 需要区分可重试、不可重试和结果未知。\
- 重试策略应由操作语义决定，不能只根据错误字符串判断。\
\
## 14.3 重试规则\
\
一般原则：\
\
- 参数错误：不重试。\
- 权限错误：不自动重试。\
- 明确的限流错误：按 `Retry-After` 或退避策略重试。\
- 只读请求超时：在安全条件下重试。\
- 交易提交超时：先对账，不得直接假定未提交。\
- 事件处理失败：按幂等语义重试。\
- 业务逻辑失败：交由应用决定是否补偿。\
\

# 15. 可观测性\
\
首期应支持标准日志、指标和健康状态，但不强制某个商业平台。\
\
## 15.1 日志\
\
日志至少包含：\
\
- 应用名称。\
- 模块名称。\
- 网络标识。\
- 操作 ID。\
- 交易 ID 或签名（如果已知）。\
- 事件 ID。\
- 操作阶段。\
- 错误类别。\
- 重试次数。\
\
禁止记录秘密材料。\
\
## 15.2 指标\
\
建议包括：\
\
- Runtime 当前状态。\
- 模块启动失败次数。\
- RPC 请求量、错误率和延迟。\
- Endpoint 健康状态。\
- 交易各状态的数量。\
- 交易确认耗时。\
- `Unknown` 状态交易数量。\
- Nonce 协调冲突次数。\
- 事件读取延迟。\
- 事件重复次数。\
- 事件处理失败次数。\
- 最终性等待时间。\
- 重组检测次数。\
- 恢复任务积压量。\
\
指标标签不得使用高基数的玩家 ID、交易 ID 或任意业务字符串。\
\
## 15.3 健康检查\
\
至少区分：\
\
- Liveness：进程是否仍正常运行。\
- Readiness：服务是否具备对外提供当前能力的条件。\
- Dependency Health：具体依赖是否可用。\
\
一个可选的 Solana 模块不可用，不应自动导致完全不使用 Solana 的游戏服务整体不健康。\
\

# 16. 测试体系\
\
## 16.1 单元测试\
\
每个模块至少测试：\
\
- 正常流程。\
- 参数边界。\
- 非法状态转换。\
- 超时。\
- 取消上下文。\
- 并发调用。\
- 资源关闭。\
- 重复调用。\
- 幂等冲突。\
- 故障恢复。\
\
## 16.2 Adapter Conformance Tests\
\
建立适配器契约测试。\
\
公共能力接口每增加一个关键语义，就应补充相应的契约测试。\
\
例如：\
\
- 网络标识正确。\
- 地址校验遵守链族语义。\
- 金额不丢失精度。\
- 交易提交结果不确定时不会错误标记失败。\
- 事件读取支持可恢复的游标。\
- 不支持的能力返回明确错误。\
- 关闭适配器后不再接受新请求。\
- 取消上下文能够传递到 RPC 调用。\
\
EVM 和 Solana 使用同一套公共语义测试，但链特有的最终性、账户模型和交易行为应有各自的专属测试。\
\
## 16.3 集成测试\
\
建议按以下层次：\
\
1. 完全离线的单元测试。\
2. 使用 Fake RPC 的协议测试。\
3. 使用本地测试节点的集成测试。\
4. 可选的测试网络验证。\
5. 生产前手动安全审查。\
\
CI 不应默认依赖公共 RPC 服务，否则网络故障会使普通代码提交无法稳定验证。\
\
## 16.4 故障注入\
\
至少模拟：\
\
- RPC 在接收交易后丢失响应。\
- RPC 在交易提交前失败。\
- 相同事件被重复返回。\
- 区块重组。\
- 数据库写入失败。\
- Worker 在状态更新前崩溃。\
- 交易确认期间进程重启。\
- 多 Worker 竞争同一操作。\
- 适配器在关闭期间仍有请求。\
- Solana 交易有效期限到期但状态未知。\
\

# 17. 可选脚手架与模板\
\
## 17.1 定位\
\
脚手架不是核心运行时的一部分，只是开发辅助工具。\
\
可以提供：\
\
- 最小 Go 项目目录。\
- 配置文件模板。\
- `main.go` 装配示例。\
- 自定义模块接口骨架。\
- 测试文件骨架。\
- CI 工作流模板。\
- 可选 EVM / Solana 示例。\
\
## 17.2 禁止事项\
\
脚手架不得：\
\
- 生成游戏业务规则。\
- 强制规定玩家、道具、战斗或经济模型。\
- 自动覆盖开发者修改过的文件。\
- 成为项目编译或运行的前置条件。\
- 在每次启动时重新生成源码。\
- 将生成器专属运行时依赖引入游戏项目。\
- 以“自动更新模板”为由静默覆盖用户代码。\
\
## 17.3 覆盖策略\
\
如果提供 `init` 或 `add-module` 等命令：\
\
- 默认只创建不存在的文件。\
- 遇到已存在文件时默认跳过并给出说明。\
- 明确提供预览或差异检查方式。\
- 覆盖操作必须显式授权。\
- 不允许静默删除文件。\
- 生成后的项目必须是普通 Go 工程，开发者可以完全脱离生成器继续维护。\
\

# 18. 首期 API 与兼容策略\
\
## 18.1 公共 API 冻结原则\
\
不要在第一天就宣称所有接口永久稳定。\
\
首期可以采用：\
\
- 核心生命周期接口保持精简。\
- 链能力接口在契约测试完成后再公开。\
- 实验性接口明确标注。\
- 公共数据结构的语义必须有文档。\
- 公开 API 的重大变更必须更新示例和迁移说明。\
\
## 18.2 兼容策略\
\
建议以语义化版本管理：\
\
- `0.x`：允许在明确记录的情况下调整 API。\
- `1.0.0`：核心生命周期、能力接口、错误分类和配置结构具备稳定契约后发布。\
- 破坏性变更必须给出迁移说明。\
- 不能仅因函数签名未变就认为语义兼容；状态机和错误语义的变化也属于兼容性问题。\
\
## 18.3 不要提前抽象的内容\
\
首期不要预先建立：\
\
- 万能多链交易 DSL。\
- 通用跨链桥协议。\
- 统一所有链的账户抽象。\
- 强制插件市场。\
- 动态下载和加载任意 Go 插件。\
- 复杂的热更新框架。\
- 固定游戏领域模型。\
- 过度泛化的 ORM 或仓储系统。\
\
先让 EVM、Solana 和自定义业务模块通过清晰接口协同工作，再根据真实需求扩展。\
\

# 19. 分阶段实施计划\
\
## Phase 0：仓库审查与架构确认\
\
目标：避免重写已有实现或凭空增加需求。\
\
任务：\
\
1. 检查 `go.mod`、现有目录、公开 API 和依赖。\
2. 检查已有测试、CI、文档和示例。\
3. 标记现有实现中符合架构要求的部分。\
4. 对照本文件建立需求矩阵。\
5. 将冲突项记录为 Architecture Decision Record（ADR）。\
6. 输出实际实施计划与受影响文件清单。\
\
交付物：\
\
- 仓库审查报告。\
- 当前实现与目标架构的差距清单。\
- 待决策项。\
- 具体实施任务列表。\
\
验收：\
\
- 不在未分析现有代码的情况下删除或重写目录。\
- 所有重大架构冲突都有记录。\
- 不存在仅凭想象推定现有功能的结论。\
\
## Phase 1：Core Runtime\
\
实现：\
\
- 应用配置。\
- 日志接口。\
- Runtime 状态机。\
- Module 接口。\
- Registry。\
- 依赖图校验。\
- 模块启动与逆序关闭。\
- 健康检查基础模型。\
- 最小可运行示例。\
\
验收：\
\
- 无模块的最小 Runtime 可以运行。\
- 一个自定义模块可以被注册、启动和关闭。\
- 缺少必需依赖时启动失败。\
- 循环依赖能被检测。\
- 模块启动失败时，已启动模块能按规则关闭。\
- 重复注册能被拒绝。\
- 不存在隐式全局单例。\
\
## Phase 2：公共链能力模型\
\
实现：\
\
- ChainFamily。\
- NetworkID。\
- Address。\
- AssetID。\
- Amount。\
- 公共错误类型。\
- 能力接口。\
- 能力声明和检测。\
- Adapter Conformance Tests。\
\
验收：\
\
- Core 不导入任何具体链 SDK。\
- 公共类型不使用浮点数表达金额。\
- EVM 与 Solana 地址不能在无校验的情况下混用。\
- 适配器可以明确声明不支持某项能力。\
- 文档说明每个公共接口的语义和错误行为。\
\
## Phase 3：EVM Adapter（只读能力优先）\
\
实现：\
\
- 多网络配置。\
- RPC 客户端。\
- Chain ID 校验。\
- 网络健康检查。\
- 区块与基础网络信息查询。\
- 原生资产余额查询。\
- Token 余额查询。\
- 合约只读调用。\
- 日志读取。\
- 基础指标。\
\
验收：\
\
- 同一 Adapter 能装配两个以上逻辑 EVM 网络。\
- 网络身份校验失败时启动或调用按设计失败。\
- 不同网络的地址、资产和交易记录不会串用。\
- RPC 超时能够被分类。\
- 单元测试不依赖真实公共 RPC。\
\
## Phase 4：Solana Adapter（只读能力优先）\
\
实现：\
\
- 独立 Solana 网络实例。\
- 集群身份校验。\
- 账户查询。\
- 原生资产余额查询。\
- SPL Token 余额查询。\
- 可用的交易或日志查询。\
- Commitment 配置。\
- 连接状态和指标。\
\
验收：\
\
- Solana 不依赖 EVM Adapter。\
- Solana 公钥和账户语义得到保留。\
- 不支持的能力返回明确错误。\
- 只读场景不需要配置写入权限。\
- 测试覆盖不同 Commitment 的处理。\
\
## Phase 5：交易能力\
\
按适配器分别实现：\
\
- 交易准备。\
- 签名器接口。\
- 交易提交。\
- 交易状态查询。\
- EVM Nonce 管理。\
- Solana Blockhash 期限管理。\
- 状态机。\
- 幂等键。\
- 持久化交易记录。\
- 结果未知的恢复逻辑。\
\
验收：\
\
- 相同幂等键不会产生重复的独立业务操作。\
- 交易提交响应丢失时进入可对账状态。\
- EVM 不会因普通并发调用重复分配同一个本地 Nonce。\
- Solana 不会因 Blockhash 过期就盲目重复业务交易。\
- 交易状态非法转换被拒绝。\
- 生产交易流程不依赖 Memory Repository。\
\
## Phase 6：事件系统\
\
实现：\
\
- 事件标准模型。\
- EVM Logs。\
- Solana 事件来源。\
- 事件持久化。\
- 游标与断点续传。\
- 去重。\
- Handler 注册。\
- 至少一次交付。\
- 重试和失败记录。\
- EVM 重组检测。\
- 事件恢复任务。\
\
验收：\
\
- 同一事件重复读取不会重复产生非幂等的框架内部状态变化。\
- 进程崩溃后可从持久化游标恢复。\
- 事件未达到要求的最终性时不会被错误标记为最终状态。\
- 重组会触发明确的状态修正流程。\
- 业务 Handler 的幂等责任和补偿边界有文档说明。\
\
## Phase 7：生产基础设施与可观测性\
\
实现：\
\
- 至少一种生产级持久化实现。\
- 指标接口。\
- 日志关联字段。\
- 健康检查。\
- 关闭超时。\
- RPC 限流与退避。\
- 多实例任务协调（如声明支持多实例）。\
- 安全配置校验。\
- 故障注入测试。\
\
验收：\
\
- 进程重启后可恢复持久化交易状态。\
- 未知交易状态可被查询和对账。\
- 不同网络的指标可以区分。\
- 日志不包含秘密材料。\
- 多实例能力声明与实际实现一致。\
\
## Phase 8：文档、示例与发布\
\
交付：\
\
- 最小应用示例。\
- 自定义模块示例。\
- EVM 只读示例。\
- EVM 交易示例。\
- Solana 只读示例。\
- 多网络示例。\
- 适配器实现指南。\
- 安全指南。\
- 故障恢复指南。\
- 版本兼容策略。\
- CI 与发布流程。\
\
验收：\
\
- 示例能够从干净环境编译。\
- 示例不要求生成器才能运行。\
- 文档中的 API 与代码一致。\
- README 清楚说明 Chame 不是固定游戏业务框架。\
- 发布包不包含不必要的秘密或开发凭证。\

# 23. 需要在实施前确认的架构决策\
\
以下事项不能凭空视为已确定，Agent 应优先检查现有仓库及依赖后提出建议，并通过 ADR 记录最终结论。\
\
1. **RPC SDK 选型**：比较维护活跃度、上下文取消、WebSocket 订阅、交易支持和许可证后决定。\
2. **持久化实现**：首个官方实现选择哪种 SQL 数据库，以及是否复用游戏项目现有数据库。\
3. **Solana 交易能力范围**：首期只读先行，还是同时交付交易构建和签名。\
4. **EVM Nonce 协调范围**：首期是否支持多实例共享账户并发写入。\
5. **事件订阅策略**：WebSocket 优先还是轮询优先，以及断线后的回补方案。\
6. **最终性策略**：各网络的默认策略、配置方式和能力限制。\
7. **可观测性实现**：只提供抽象，还是同时提供一个官方指标导出器。\
8. **公开 API 稳定范围**：哪些包首期对外承诺兼容，哪些暂时属于内部实现。\
\
这些决策应有明确理由、替代方案、影响范围和测试要求。\

# 24. 最终架构结论\
\
Chame 的核心竞争力不应该是把所有链都包装成相同的 API，而应该是：\
\
1. 给游戏开发者提供稳定、精简的 Go 后端运行基础。\
2. 通过明确的能力接口接入多种区块链。\
3. 保留各链真正重要的协议差异。\
4. 为交易、事件、幂等和恢复提供可验证的基础设施。\
5. 让开发者完全自由地实现自己的游戏业务。\
6. 让模块与适配器可以替换、扩展和独立测试。\
7. 在首期保持足够小的实现范围，避免为了未来可能的需求过度设计。\
\
**实施顺序应是：仓库审查 → Runtime → 公共能力契约 → EVM 只读 → Solana 只读 → 交易可靠性 → 事件处理 → 生产基础设施 → 文档与发布。**\
\
不要先实现庞大的多链万能抽象，再试图让真实链行为适配它。应当从清晰的公共契约和真实的 EVM、Solana 行为出发，逐步验证并稳定 Chame 的框架边界。\

\
\
type Module interface {\
    Name() string\
    Register(Registry) error\
    Start(context.Context) error\
    Stop(context.Context) error\
}\
```\
\
其中：\
\
- `Name()` 返回稳定且唯一的模块标识。\
- `Register()` 注册模块声明的能力、服务和处理器，不应偷偷启动长期后台任务。\
- `Start()` 在依赖完成初始化后启动模块。\
- `Stop()` 释放模块持有的资源，并遵守传入的关闭期限。\
\
`Registry` 必须提供受控的注册功能，至少包括：\
\
- 注册和读取具名能力。\
- 注册事件处理器。\
- 注册健康检查。\
- 注册后台任务。\
- 注册模块元数据。\
- 检查重复名称和重复注册。\
\
不要将 `Registry` 做成任何模块都可以任意修改其他模块内部状态的万能容器。\
\
## 4.4 模块依赖\
\
每个模块可声明：\
\
```go\
type Dependency struct {\
    Name     string\
    Optional bool\
}\
```\
\
模块注册信息应允许声明：\
\
- 模块名称。\
- 依赖列表。\
- 所需能力。\
- 提供的能力。\
- 配置 Schema 或配置校验器。\
- 健康检查。\
- 生命周期超时。\
\
启动前执行：\
\
1. 校验名称唯一。\
2. 校验必需依赖是否存在。\
3. 校验能力是否唯一或符合多提供方策略。\
4. 构建依赖有向图。\
5. 检查循环依赖。\
6. 计算启动顺序。\
7. 计算逆序关闭顺序。\
\
如果依赖图有环，必须在启动任何外部服务之前失败，并输出清晰的环路信息。\
\
首期不需要复杂的自动依赖注入容器。显式装配依赖优先于反射式魔法。\
\
## 4.5 优雅关闭\
\
Runtime 的关闭顺序：\
\
1. 停止接受新任务。\
2. 通知模块进入停止阶段。\
3. 停止事件消费者和定时调度器。\
4. 等待允许完成的在途工作。\
5. 关闭链 RPC、数据库、HTTP Server 等资源。\
6. 汇总关闭错误。\
7. 将状态切换为 `Stopped`。\
\
必须设置总体关闭超时。单个模块不能无限阻塞整个进程。\
\
如果任务没有完成，应留下可恢复状态，不能通过将未完成任务直接标记成功来结束进程。\
