# ADR-0008: 首期公开 API 稳定范围

- 状态：已接受（代决，用户可推翻）
- 日期：2026-10-15
- 对应规格：§18、§23 第 8 项

## 背景

§23 要求明确哪些包首期对外承诺兼容，哪些属于内部实现。§18.1 同时规定公共 API 冻结原则。

## 决策

**首期承诺兼容（破坏性变更需 ADR + 变更日志）**：

- 根包 `chame`
- `core/*`：runtime、module、config、errors、identifiers、clock、logging、health、lifecycle 的公开接口
- `capability/*`：全部公开契约

**内部实现（不承诺兼容，不另行通知变更）**：

- `application/*`
- `adapters/*` 的公开类型（SDK 类型隔离边界内的部分）
- `infrastructure/*` 全部实现
- 任何包内 `internal/` 目录

**版本语义**：语义化版本只对用户手动触发的 tag 生效（红线：版本号只能由用户给出）；无 tag 期间不承诺兼容，仅按上述范围尽善意的稳定努力。

## 理由

- 公共面越小，冻结成本越低（§18.3：不提前抽象）。
- application/adapters/infrastructure 还会随阶段推进演化，纳入兼容承诺会拖慢实现。
- 首期使用者在自己的业务代码里应当只 import 承诺范围 + 适配器装配入口。

## 备选方案

- **全部导出包都承诺兼容**：否。范围过大，与 §18.3 冲突。
- **只承诺根包**：否。capability 契约是框架核心价值，必须稳定。

## 影响范围

- 文档（README 与包文档）需标注每个包的稳定性级别。
- `application/`、`infrastructure/` 后续若稳定，通过新 ADR 扩大承诺范围，不回缩。

## 测试要求

- 承诺范围内的包公开 API 变更时，CI 编译检查 examples 与 conformance 套件不破坏（示例编译检查，§20 第 6 项）。
- 包文档中的稳定性标注与本 ADR 一致性检查（人工评审，逐步自动化）。
